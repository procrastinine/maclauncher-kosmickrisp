# KosmicKrisp external memory

MacLauncher KosmicKrisp implements `VK_KHR_external_memory_fd` with the `OPAQUE_FD` memory handle type. Exported descriptors retain the shared allocation independently of the exporting Vulkan object and process. Each export returns a new close-on-exec descriptor. A successful import consumes the supplied descriptor; a rejected import leaves ownership with the caller. Imported memory can be exported again when the allocation requests that capability.

The backing is an unlinked shared-memory object mapped into each process and wrapped by a no-copy Metal buffer. The allocation stores a 64 KiB metadata prefix and a page-aligned payload. Metadata identifies its format version, allocation size, memory type, compatible device and driver, and dedicated-resource description. A receiver validates these fields before importing. `OPAQUE_FD` is private to compatible KosmicKrisp builds on the same GPU; it is not a Linux dma-buf or a serialized Metal heap. `vkGetMemoryFdPropertiesKHR` does not accept `OPAQUE_FD`, as specified by Vulkan.

Buffers retain normal byte-addressed binding and suballocation semantics. External images use buffer-backed Metal textures with a matching shared byte layout, including images created with Vulkan optimal tiling. Supported images are two-dimensional native color formats with one mip level, one array layer and one sample. Queries intersect the format's existing capabilities with this backing's limits. Compressed, depth/stencil, multi-plane, emulated RGB32, sparse and protected images, and input-attachment usage, are outside this backing. Supported image flags are mutable format, extended usage and aliasing. Linear images retain their existing linear-usage restrictions. Image resource-size queries are bounded by Metal's buffer limit.

External FD allocations use the same BO residency registration and allocation-priority handling as other device memory. The default priority is 0.5; an explicit allocation priority applies to imported and exported memory.

External allocation uses physically shared backing for both Vulkan memory types. CPU mapping remains available only for the host-visible type. Ordinary allocations retain the [memory storage policy](kosmickrisp-memory.md). External descriptors, mappings and allocation metadata are created only for external resources; shader code, pipeline layouts, command uploads and draw encoding use the existing paths.

Memory sharing does not supply external synchronization. Applications must order access and transfer external queue-family ownership as required by Vulkan. `SYNC_FD` semaphore/fence support is separate from persistent `OPAQUE_FD` semaphore and fence payloads. Windows shared-resource translation additionally requires a compatible Wine host driver that maps Win32 requests to the corresponding FD interfaces.
