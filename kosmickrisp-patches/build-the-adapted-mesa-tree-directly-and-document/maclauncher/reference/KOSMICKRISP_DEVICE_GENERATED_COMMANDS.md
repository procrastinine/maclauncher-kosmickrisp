# Device-generated commands

MacLauncher KosmicKrisp MCLv12 provides `VK_EXT_device_generated_commands` for vertex, tessellation, geometry and fragment stages, and for compute pipelines. The token stream can change push constants, supply a sequence index, bind vertex or index buffers, and issue draws, indexed draws or compute dispatches. Both Vulkan and DXGI index formats are accepted.

A compute pass snapshots the token data into the application's preprocess buffer. Explicit preprocessing retains that snapshot for a later execution command; implicit preprocessing performs the same operation during execution. Execution captures the matching bound descriptor and push state once. Internal descriptor uploads belong to the executing command buffer; the persistent snapshot contains no pointers into a preprocessing command buffer. When commands execute, a second compute pass expands at most 16,384 sequences into temporary roots, draw data and a Metal indirect command buffer. Each command receives its own push data and buffer addresses without a CPU readback.

The graphics path uses the ordinary attachment, pipeline and dynamic state flush. Ordinary pipelines keep their normal Metal configuration. An ICB-capable pipeline copy is cached on first generated use and prepared eagerly for an indirect-bindable pipeline. Both copies share their shader sources and attachment selection. Graphics pipelines using dependent descriptor-address loads use the shared generated-root draw replay because the Metal indirect uniform ABI cannot compile those loads. Geometry, tessellation and primitive conversion run through the existing Mesa Poly draw path with a generated descriptor root. Vulkan-format generated index bindings, including 8-bit indices, are resolved on the GPU into a reserved prefix of the same Poly heap. DXGI index tokens retain native ICB execution for 16-bit and 32-bit indices. Compute commands retain the bound local workgroup size. Sequence counts are clamped to the supplied maximum, and conditional rendering predicates execution. A GPU-written execution range limits each ICB to its active sequences; inactive sequences do not expand descriptor roots or enter Metal command execution. The temporary resources belong to the recording command buffer and are released when its resources are reset or destroyed.

The reported limits are 1,048,576 generated sequences, 128 tokens, a maximum token offset of 4,095 bytes and an indirect stream stride of 4,096 bytes. Indirect execution sets, indirect pipeline or shader-object binding, generated-command transform feedback and COUNT action tokens are outside this profile.

Ordinary indirect draws support `maxDrawIndirectCount = 1,073,741,824`. Large native draw-count commands use the same bounded GPU expansion and ICB mechanism. Poly, primitive-restart and query recording use bounded batches while preserving the original draw indices and count predicate. Ordinary direct draws retain the shared draw path.

The layout representation comes from Mesa's Vulkan runtime at the selected source pin. Metal ICB construction follows the mechanism described by the MoltenVK adaptation in [MetalSharp VKD3D-Proton-MacOS](https://github.com/metalsharp/VKD3D-Proton-MacOS/tree/4e89065e359f9c6c2a78170b045835d6382113d9). The capability module and its source inputs are listed in the [adaptation catalog](../../src/kosmickrisp/).

Linked graphics stages use two wrapper-buffer GPU addresses supplied by the selected pipeline-cache entry. Each generated graphics command binds the vertex wrapper at buffer index 3 and the fragment wrapper at buffer index 4. The addresses are captured after the shared graphics flush selects the indirect-capable pipeline variant. Both addresses default to zero when linked tables are absent.

The interlock guard has a separate per-command binding at the shared guard slot. It does not replace either linked-stage wrapper buffer. Ordinary argument tables and indirect-command descriptors use the shared usage-based capacity calculation.

Graphics sequences targeting layered attachment aliases use the shared producer and retained raster-reader path. GPU-generated counts, predicates and token state remain in indirect records. Each sequence completes its logical-layer raster readers before the following sequence can reuse the preparation heap or generated-record scratch.
