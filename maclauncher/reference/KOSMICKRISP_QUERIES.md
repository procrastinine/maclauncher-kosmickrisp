# KosmicKrisp query accounting

The implementation is part of the Mesa source tree. Package provenance records the exact fork commit.

Occlusion queries use the device visibility buffer and per-pool remapped indices. Timestamp queries use Metal counter heaps and a result sentinel for availability. Transform-feedback queries store two reports per query; generated-primitive queries store one. Result reads and copies preserve the requested 32-bit or 64-bit width and availability. Partial results follow the rules of each query type.

Timestamp pools span multiple native counter heaps when necessary. Heap capacity comes from actual successful Metal allocations and the returned native count; the Vulkan query count remains unchanged. Each write selects its native heap and local slot. Reused render-stage timestamps retain both that heap and slot, including when the destination query lies in another chunk. Resets, availability, host reads and GPU copies use the shared linear Vulkan report buffer, so ranges can cross native heap boundaries. Pools that fit one heap keep the ordinary single-heap allocation and index path.

All eleven core statistics have producers based on Mesa's Honeykrisp and shared Poly implementation at the pinned source revision. Reports are packed in statistic-bit order, with one 64-bit accumulator per selected statistic and separate availability words. Statistics from shader stages absent from the application pipeline remain zero, including internally generated geometry stages.

Input-assembly and vertex statistics use the actual draw arguments, topology and index/restart data. Geometry statistics use the original emitted-primitive counts before transform-feedback capacity limits and polygon expansion. Tessellation statistics use the executed patch and generated domain-point counts. Clipping statistics follow Honeykrisp's implementation-dependent counting model using actual assembled or emitted primitives. They do not measure Metal's internal clipping or replay operations.

Devices created with `pipelineStatisticsQuery` enabled compile fragment entry counters after the application's fragment and helper-invocation lowering. Devices that leave the feature disabled skip this pass. A Metal function constant defaults to false and encloses the complete counter region, including its root-address load. An active fragment-invocation query selects a cached counting specialization; its first use compiles that specialization from the existing library. Query-free draws retain the ordinary specialization. Existing framebuffer-read color constants remain in the descriptor chain. Actual application-function metadata controls specialization independently for each native program; capture, replay and support entry points do not inherit application counts. The device feature state and statistics shader ABI participate in the [shared shader cache key](KOSMICKRISP_SHADER_CACHE.md), independently of sampler reduction.

Metal suppresses atomic writes from helper threads. The private query increment adds no helper-status or coverage input and preserves the application's demote, derivative and explicit early-test behavior. Captured application bodies reuse their existing logical-helper predicate. A pair of 32-bit atomic operations carries into the 64-bit report. Compute statistics use the product of the dispatched workgroup counts and local dimensions. Indirect and predicated dispatches consume the same GPU arguments as the application dispatch. Base-workgroup offsets and internal helper dispatches do not contribute.

The driver exposes `pipelineStatisticsQuery`. Active queries add the relevant GPU counting helpers, per-draw geometry/tessellation counter storage and ordering barriers. Tessellation uses a zero statistic address without an active TES counter and allocates no statistics scratch. Geometry statistics occupy an optional four-address tail after the ordinary per-draw fields. Query-free draws omit its initialization and upload. The pre-GS patch-up program defaults to a specialization with those address loads disabled; an active GS or clipping query selects its lazily cached counting pipeline. Its retained function and counting handle occupy storage only for an actual compiled GS statistics consumer. The main GS and count programs share their ordinary pipelines. Active GS or clipping queries add four 32-bit scratch counters to the existing stream scratch, preserving XFB and generated-primitive reports. The stream parameter layout is unchanged by statistics gating. Packed report offsets are computed once when the pool is created. Counting uses the existing queue, compiler, descriptor and query-copy machinery, with no CPU readback during recording or separate GPU queue.

The adaptation reuses Mesa MIT-licensed Honeykrisp and Poly source, retaining attribution in the owned sources. Timestamps, visibility samples and fabricated zero substitutions do not replace pipeline statistics.
