# Recorded scene operations

The neutral native exports rsVulkanSceneOperationAPI and rsVulkanRecordSceneOperation record optional scene processing on the Vulkan producer's device and Metal4 submission queue. Operation API3 adds a submitted callback while retaining API2 records with version2 callbacks. Both use the unchanged RSVulkanSceneEncodingV2 payload. API3 records use RSVulkanSceneOperationV3 and RSVulkanSceneCallbacksV3 with version3 prefixes; their extended sizes must match. Staging API0 requires native-compatible resources.

An operation supplies actual image handles with one aspect, mip and array layer per binding. Supported bindings resolve to single-sample two-dimensional native views. Scalar frame, color, AOV and matrix metadata are copied without inferred depth, motion, camera or color conventions. Declared AOV slots require an accompanying packet and real image binding. Sparse, memoryless and unsupported native views return unsupported.

The operation remains in command order and executes through the ordinary command replay pool. Each execution has distinct stable result storage and retained native resources, allocator, residency and queue. Completion, failure and abandonment retire each execution once. Reset releases the recording independently of submitted flights. Native dependencies order the operation with producer work; no separate queue or image readback is used.

Ordinary API2/API3 observer records require original-output-retained operations. Native rsVulkanQuerySceneFeature3 calls the supplied selected-provider shape query on the actual retained Metal device without resolving images or recording commands. Query success has encoded0 and transfers no admission or output lease. Native rsVulkanPrepareSceneOperation3 resolves device-bound inputs without commands and calls the paired common preparation function. Successful preparation returns an owned RSRecordedSceneConsumerV3 lease only after actual provider/output admission. Records using this driver-issued lease may omit the original-output-retained flag; the immutable request, output shape and subresources must still match. The retained lease reuses the exact prepared views through recording replay and flight retirement. Busy or rejected preparation transfers no admission. Vulkan record success means recorded. It does not establish provider preparation, output fulfillment, NGX replacement availability, frame generation or presentation ownership. Provider selection and output admission belong to the supplied common scene callback. API2 reports GPU completion. API3 also reports submission with the exact result identity and a retained native shared event at value1. The signal follows the final producer commit on its existing queue, including a deferred interlock tail. Failure or abandonment before commit reports no accepted event. Completion follows submission notification; common output consumers retain accepted events through their own retirement.

Generation preparation carries the existing submission metadata and typed Vulkan output bindings. The driver resolves these targets on the producer device, reuses the scene output for the first target and retains additional targets in the admitted resource lease. Algorithm history sequence is independent of the recorded frame, result and flight identities. Sequence, phases and count pass to the existing native generation preparation contract. Execution uses the admitted operation owner. History warmup does not establish synthetic output fulfillment.

A scene operation may first appear after ordinary native commands or through a secondary command buffer. Direct one-time recording retains its native prefix and allocator in the existing command-part storage, then keeps only the remaining commands as IR. Submission continues the original command's CPU state on the actual queue and commits the ordered prefix and suffix together. No submit-owned scene callback runs during recording. Recording summaries propagate through secondary execution without scanning the complete command list at End.

Stable result and output leases are independent of native command storage. Legal reset after GPU completion closes retained native storage before allocator reuse, even when a common output lease remains held; completion or failure closes it once through the same path. Native finalization is shared by ordinary End and the submit-owned suffix.
